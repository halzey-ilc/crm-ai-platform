Дата: 2026-10-28. Метод: чтение схем и кода CRM, плюс **только количества строк**
в базах локального стека CRM (`docker exec … psql`, read-only). Содержимое записей
не читалось и не копировалось. Персональные данные в отчёт не попали.

## 1. Итог

**Реальных данных для обучения нет.** Локальный стек CRM содержит одну демо-компанию,
одного клиента и одного пользователя. Production-данные недоступны и не
запрашивались. Поэтому первым результатом стал **работающий pipeline подготовки
данных и обучения на синтетических данных**, а не обученная модель
([TRAINING_STRATEGY.md](TRAINING_STRATEGY.md)).

## 4. Риски качества и утечки целевой переменной

| Задача | Поля-утечки (запрещены как признаки) |
|---|---|
| Lead scoring | `status`, `converted_customer_id`, `disqualify_reason`, `updated_at` (меняется при конверсии) |
| Win/loss сделки | `closed_at`, `lost_reason`, текущий `stage` и `probability` на момент закрытия, `updated_at`, счета по `deal_id` |

Эти поля внесены в `forbidden_columns` конфигурации эксперимента. Toolkit
отказывается работать, если такой столбец присутствует в датасете или указан
как признак. ✅ (`test_leaking_column_is_blocking`, `test_config_rejects_forbidden_feature`)

Признаки должны браться **на момент прогноза** (point-in-time). Для этого
нужна история изменений: сейчас её дают только события outbox.

## 5. Privacy и изоляция компаний

- Модель хранения: отдельная база на компанию. Межтенантные данные для общей модели
  **не смешиваются автоматически** и требуют документированного основания
  ([AI_DATA_GOVERNANCE.md](AI_DATA_GOVERNANCE.md)).
- Логи CRM уже вырезают текст сообщений и аудио (redaction filter).
- Не определены: цели использования данных для обучения, сроки хранения, порядок удаления по
  запросу и экспорт. Всё это требует решения владельца.

## 6. Возможные первые задачи (по готовности)

| Задача | Данные | Объективная метрика | Готовность |
|---|---|---|---|
| A. Lead scoring | Лиды с исходом | ROC AUC, PR AUC, калибровка против baseline | ⛔ данных 0; pipeline готов на синтетике ✅ |
| B. Классификация звонков | Транскрипты + разметка | macro-F1 по классам, отдельно ru и ky | ⛔ нет транскриптов |
| C. Извлечение из звонков | Транскрипты + эталон полей | точность по полям, доля привязки к источнику | ⛔ нет транскриптов; контракт и проверка привязки ✅ |
| D. Аномалии KPI | История `KpiSnapshotRecord` | precision на размеченных инцидентах против правил | ⛔ истории нет |

**Рекомендация:** первой реальной моделью выбрать **A (lead scoring, классический ML)**:
у неё есть метка в схеме, табличные признаки и проверяемая метрика. Это возможно
только после накопления реальных лидов с исходами и добавления в CRM времени
конверсии (или выгрузки истории из outbox).

## 7. Критерии достаточности (lead scoring, ориентир)

Универсального минимума нет. Для этой задачи достаточность проверяется на данных:
- не меньше нескольких сотен положительных исходов (конверсий) **в одной компании** за
  период, сопоставимый с циклом продаж; в конфигурации стоит порог `min_positives`, ниже
  которого обучение отклоняется;
- временной охват не меньше 2–3 циклов продаж, чтобы сделать честный временной split;
- модель на валидации устойчиво превосходит baseline (prior и простое правило по источнику);
  иначе модель не нужна.

4. Согласовать выгрузку обезличенного датасета одной компании для пилота (с согласия компании).
