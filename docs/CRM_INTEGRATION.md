# Интеграция с CRM Backend

Источник фактов — чтение кода CRM (`/home/user/crm-platform`, коммит `588431e`,
2026-10-28). Статусы — [STATUS_LEGEND.md](STATUS_LEGEND.md).

## 0. Реализовано: этап 1 — резюме звонка (✅, в `main` CRM, коммит `59892ec`)

По согласованию владельца в CRM добавлен модуль `modules.ai_insights`
(описание: `crm-platform/docs/architecture/ai-integration.md`). Выбрана схема
**«CRM забирает результат»** вместо предложенной в §3.2 записи результатов из
AI Platform в CRM:

- CRM проверяет видимость звонка и право `ai.request`, затем в фоновой задаче (очередь
  `integrations`) отправляет `POST /v1/jobs` с 5-минутным токеном §3.1 (tenant — активная
  компания CRM, `sub` — пользователь) и опрашивает `GET /v1/jobs/{id}` до результата.
- У AI Platform **нет ни одного ключа или права доступа к CRM**; в CRM не появилось
  нового входящего эндпоинта для сервиса.
- Результат (`call_summary.output.v1`) хранится в базе компании в CRM вместе с `is_mock`,
  провайдером и моделью.
- Функция выключена по умолчанию (`AI_PLATFORM_ENABLED`).

Проверено: 307 тестов CRM (включая новые unit, API и тесты изоляции) и сквозной сценарий
`scripts/e2e_with_crm.sh`. Сценарий: CRM → AI Platform → CRM на двух живых стеках,
связанных сетью `crm-ai-link`, где есть только gateway.

**Этап 2 — AI Operations (✅, в `main` CRM, коммит `2c6cf0b`).** Схема та же: CRM
забирает результат. Правила считает CRM (модуль `operations`). В AI уходят только
ссылки `lead:<uuid>`, `deal:<uuid>`, `task:<uuid>`, виды нарушений, возраст и пороги
(`operations.digest.v1`). Сводка личная: каждый видит только свою. Ежедневный запуск
в 06:00 — только для тех, у кого есть право `ai.request` и есть нарушения.

Пункты §3.2 и §3.3 ниже остаются вариантами на будущее (для событийных сценариев AI
Operations), а не обязательными требованиями.

## 1. Что реально есть в CRM

- **API.** REST `api/v1/`, OpenAPI через drf-spectacular (`/api/schema/`, только local/test).
  Пагинация LimitOffset по 50. Версия API только `v1`.
- **Аутентификация.** Пользовательский JWT (SimpleJWT, HS256, issuer/audience). Компания
  выбирается заголовком `X-Tenant: <slug>`, после чего CRM проверяет членство. В JWT нет
  tenant и роли.
- **Межсервисной аутентификации нет:** ни API-ключей, ни сервисных аккаунтов, ни client
  credentials, ни mTLS.
- **Мультитенантность.** Отдельная PostgreSQL-база на компанию (`crm_tenant_<slug>`), роутер
  fail-closed. Чужая или неизвестная компания возвращает 404.
- **События.** Transactional outbox → RabbitMQ (`events`), около 30 типов событий. В payload
  только идентификаторы. **Внешний подписчик невозможен:** нет исходящих вебхуков и
  event-stream эндпоинта.
- **Фильтров `updated_since` нет:** инкрементальная синхронизация через API невозможна.
- **Звонки (`telephony`).** Хранится `recording_url` (строка), аудио нет, **транскриптов нет**,
  полей согласия нет. Входящие вебхуки телефонии сохраняются, но не разбираются.
- **Сообщения (`communications`).** Полный текст сообщений, каналы WhatsApp, Telegram,
  Instagram, email (для email парсера нет).
- **RBAC.** Роли owner, admin, manager, sales_rep, viewer с областями own, team, all.
  **TEAM фактически работает как OWN** (нет модели команд).

## 3. Предлагаемые контракты (требуют изменения CRM — не реализованы)

### 3.1 Сервис-токен CRM → AI Platform

📐 CRM, проверив пользователя и его членство, выпускает **короткий** (≤ 10 мин)
HS256-токен для AI Platform:

```json
{ "iss": "crm-platform", "aud": "crm-ai-platform", "sub": "user:<uuid>",
  "tenant": "<slug>", "scope": "ai.jobs.create ai.jobs.read",
  "iat": 1761650000, "exp": 1761650600, "jti": "<uuid>" }
```

AI Platform уже проверяет такой токен: подпись, `iss`, `aud`, `exp`, срок жизни
≤ `AI_AUTH_MAX_TOKEN_TTL`, формат tenant, scopes. Это ✅ в коде, токены в тестах
выпускаются `tools/devtoken`. На стороне CRM нужно: общий секрет
`AI_AUTH_HS256_KEY` (отдельный от `JWT_SIGNING_KEY` CRM) и функция выпуска
токена. Альтернатива на будущее — асимметричная подпись (EdDSA/RS256), чтобы
AI Platform не могла выпускать токены сама.

### 3.2 AI Platform → CRM: запись результатов

📐 Новый эндпоинт CRM (пример для звонков):

```
POST /api/v1/telephony/calls/<call_id>/ai-results/
Authorization: Bearer <service token, scope ai.results.write, tenant=<slug>>
Idempotency-Key: <ai job id>
{ "schema": "call_summary.output.v1", "job_id": "...", "model": "...", "is_mock": false, "output": { ... } }
```

CRM сама решает, что делать с результатом (показать менеджеру, не создавать
задачи автоматически). Нужно: сервисная идентичность в CRM с правами
**только** на этот эндпоинт и только для компании из токена.

### 3.3 Доставка событий CRM → AI Platform

📐 Варианты (выбор требует согласования):
1. **Исходящий вебхук из outbox-обработчика CRM** с HMAC-подписью. Проще всего и не требует
   общего брокера. Предпочтительно.
2. Отдельная очередь RabbitMQ CRM для AI. Связывает инфраструктуры, не рекомендуется.
3. Опрос API. Невозможен без фильтра `updated_since`.
